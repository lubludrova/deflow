# DEFlow rebuttal

Работаем из `~/dev/DEFLOW`. Вся rebuttal-работа находится здесь, в четырёх папках.

| Что нужно | Открыть |
| --- | --- |
| Все 35 замечаний, заметки и следующие проверки | [common/ISSUES.md](common/ISSUES.md) |
| Ответ конкретному рецензенту | [VrBX / R1](reviewers/VrBX.md), [dkt6 / R2](reviewers/dkt6.md), [agWk / R3](reviewers/agWk.md) |
| Текущие эксперименты и результаты | [E01: solver comparison](experiments/E01-solver-comparison/README.md) |
| Состояние сервера и синхронизации | [common/operations](common/operations/README.md) |
| Передать работу следующему агенту | [RUNNER_HANDOFF.md](RUNNER_HANDOFF.md) |

## Структура

```text
rebuttal/
├── README.md
├── RUNNER_HANDOFF.md
├── common/
│   ├── ISSUES.md             единая доска замечаний и общих задач
│   ├── response-notes.md     общие правила для черновиков
│   ├── sources/              статья, оригинальные отзывы, screenshots
│   ├── evidence/             общие проверки статьи и кода
│   └── operations/           активный профиль, status и синхронизация
├── reviewers/
│   ├── VrBX.md               рабочий ответ R1
│   ├── dkt6.md               рабочий ответ R2
│   └── agWk.md               рабочий ответ R3
├── experiments/
│   └── E01-solver-comparison/
│       ├── README.md         вопрос, протокол, результаты и ограничения
│       ├── code/             исходный baseline package
│       ├── runs/             кампания целиком, включая её frozen source
│       └── analysis/         доступ к отчётам, коду анализа и замерам
└── archive/                  старые планы, handoffs и история организации
```

`common` — то, что нужно нескольким ответам. `reviewers` — только тексты ответов. `experiments` — общие исследовательские вопросы и их доказательства. `archive` — история, которую обычно не нужно открывать.

## Как работать

1. Найти замечание по ID в [ISSUES.md](common/ISSUES.md), сверить с [оригинальным отзывом](common/sources/REVIEWS_RAW.md), записать идею ответа и необходимую проверку.
2. Использовать существующий эксперимент или создать следующий `E<NN>-<question>`, например `E02-<question>`. В его README указать вопрос, IDs замечаний, протокол, статус, результаты и ограничения. Новый научный запуск требует отдельного разрешения, если он не входит в действующий контракт.
3. Хранить данные один раз в эксперименте. Если он нужен двум рецензентам, сослаться на него из двух строк доски и двух ответов.
4. Обновить соответствующий файл в `reviewers/`. Сначала дать прямой ответ, затем доказательство и границы вывода. Общие правила собраны в [response-notes.md](common/response-notes.md).
5. Перед отправкой пройти все 35 IDs, проверить числа, сократить текст и сверить действующие требования площадки. Ответ должен быть понятен рецензентам и Area Chair. Финальная отправленная версия пока не создана.

Это применение процесса из [How we write rebuttals — Parikh, Batra, Lee](https://deviparikh.medium.com/how-we-write-rebuttals-dc84742fece1): общий разбор замечаний, идеи ответов, черновик, затем проверка покрытия и сокращение. Идея, пилот или написанный ответ не означают, что научный вопрос закрыт.

## Проверить текущую кампанию

Из корня `~/dev/DEFLOW`:

```bash
python3 rebuttal/common/operations/status.py
```

Команда только читает сервер. Точный профиль доступен в [active_campaign.json](common/operations/active_campaign.json), также через `.agents/remote-experiment.json` в корне репозитория. Не восстанавливать живой статус из старых сообщений или планов.

## Что сохранено

Работающая кампания E01 сохранена целиком внутри `runs/`. Её исходники и научный контракт не менялись. `analysis/` содержит две относительные ссылки на исходные каталоги отчётов внутри кампании, без копирования тяжёлых данных.

Все прежние документы и история переноса доступны в [archive](archive/README.md). Пять старых внешних путей оставлены как совместимые ссылки для frozen contract. Не удалять их во время текущей кампании. Полный raw новой кампании хранится на сервере, локальный mirror компактен. Ничего не удалено ради упрощения.
