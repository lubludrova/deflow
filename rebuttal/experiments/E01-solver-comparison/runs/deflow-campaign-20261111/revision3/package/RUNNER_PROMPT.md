Сначала проверь перенос и окружение, затем запускай очередь без повторного согласования уже заданных настроек. Если сервер или разрешённые GPU ещё не указаны, запроси только эти недостающие данные.

## 2. Какие эксперименты выполнить

Все научные запуски — **с нуля**, wide-tight (`MultiGoalDockTight-v0`), по **200 000 реальных переходов**, seeds **1, 2, 3**. Новый solver меняет только forward solve. Backward, density safeguards и остальные настройки обучения сохраняются.

| Обозначение | Режим | Настройки | Зачем |
|---|---|---|---|
| N | Sequential Newton | rtol=1e-5, atol=1e-7, cap=25 | Сравнить последовательный solver с joint Anderson |
| A | Исходный Anderson | tol=1e-5, cap=25 | Свежий контроль на том же сервере с той же диагностикой |
| H | Anderson с большим лимитом | tol=1e-5, cap=500 | Проверить влияние ограничения в 25 итераций |
| T | Anderson tighter | tol=1e-6, cap=100 | Дополнительная чувствительность к более строгой точности и другому бюджету |

Каждая строка — три seed, всего **12 запусков**. Приоритет: N/A, затем H, затем T. Если ночного окна не хватает, отложи целые запуски T, затем H. Не сокращай горизонт и не выбирай seeds по получившейся награде. Уже начатый запуск не останавливай просто из-за окончания ночи, если пользователь не задал жёсткий срок аренды.

## 3. Проверки перед очередью

1. Проверь доступ к выделенным GPU, свободную память и диск. Создай отдельное окружение, запиши версии Python/PyTorch/CUDA и модели GPU. Не меняй чужие окружения и процессы.
2. Сверь исходники с `engine_sha256.json` и пакет с `VALIDATION_CONVERGENCE.json`. При несовпадении выясни причину. Не переписывай ожидаемые хеши для обхода проверки.
3. Из `PACKAGE` выполни `python -m pytest -q deflow_rebuttal/test_solver.py deflow_rebuttal/test_audit.py` с заданным `DEFLOW_ENGINE`. Ожидаются **16 passed, без skipped**.
4. Для каждого из четырёх режимов сделай отдельный `--smoke --execute`, seed=0. Smoke — 256 переходов с маленьким батчем. Проверь actor updates, checkpoint, телеметрию и короткую оценку через `evaluate` на 4 эпизодах. Smoke допускает CPU, поэтому обязательно проверь фактический `device=cuda` в логе. Локально проверен CPU с Torch 2.13, серверная CUDA-проверка ещё нужна.
5. Сделай отдельный timing pilot каждого режима: seed=0, `--steps 8000 --execute`, **без `--smoke`**, с обычным batch=1024. Оцени скорость после learning_starts=4000, а не только быстрый сбор случайных действий. Pilot не включай в научные результаты. Сообщи предварительный ETA с запасом и обновляй его по ходу обучения: ранний pilot не гарантирует стоимость поздних решений с cap=500.

Технические проблемы установки можно исправлять в новом окружении. Если тесты или численные проверки не проходят, сохрани диагностику и останови зависимые запуски. Не меняй научные настройки ради прохождения проверки.

## 4. Как запускать и распределять GPU

Один trainer на GPU. Закрепи seed за одной физической картой:

| Логический слот | Seed | Последовательная очередь |
|---|---:|---|
| 0 | 1 | N1 → A1 → H1 → T1 |
| 1 | 2 | A2 → N2 → H2 → T2 |
| 2 | 3 | N3 → A3 → H3 → T3 |

Слоты 0/1/2 — не обязательно физические GPU 0/1/2. Сохрани соответствие выделенным картам и задавай `CUDA_VISIBLE_DEVICES` отдельно каждому процессу. Внутри такого процесса `cuda:0` — назначенная ему карта. Каждая карта выполняет свою очередь независимо.

Бери `argv` задачи из `night_campaign.json`, заменяй `{REPO}` и `{OUTPUT}` серверными путями, а `python` — интерпретатором подготовленного окружения. Сначала проверь команду с `--plan` вместо `--execute`. Затем выполни исходную команду с `--execute` в persistent session. Не запускай обучение напрямую через старый launcher DEFlow: так потеряется новый solver и его диагностика.

У каждой задачи должен быть новый output-каталог. Сохраняй команду, GPU, PID, exit code, stdout/stderr и время начала/окончания. Внешний stdout/stderr размещай рядом с output-каталогом, не создавая заранее сам каталог задачи: программа создаёт его и отказывается перезаписывать существующий.

После обучения оцени модель на той же свободной GPU и только потом запускай следующую задачу этого слота. Не совмещай обучение с другим trainer или аудитом на той же карте. Периодически проверяй прогресс и синхронизируй артефакты. При ошибке сохрани `FAILED.json`, логи и частичные результаты. Не повторяй научный запуск автоматически, не подменяй seed и не делай resume: текущий entrypoint его не поддерживает. Останови очередь затронутого слота и сообщи причину, остальные исправные слоты могут продолжать.

## 5. Когда считать запуск законченным

Выход процесса без ошибки сам по себе недостаточен. Проверь:

- Есть `DONE.json` и указанный в нём checkpoint с фактическим шагом от 200000 до 200007. Бери путь из `checkpoints[].path`, не угадывай имя файла.
- Сохранены `manifest.json`, `actor_kwargs.json`, `solver_calls.jsonl`, `telemetry_summary.json`, checkpoints и capsules.
- Выполнен `python -m deflow_rebuttal.evaluate` с `--repo REPO --run RUN_DIR --checkpoint CHECKPOINT --output NEW_EVAL_DIR --episodes 1000 --eval-seed 26152 --device cuda`.
- Есть `evaluation.json` с 1000 эпизодами и U4/success/return. Оценщик сам восстанавливает solver и его настройки. Не используй старый evaluator, который может восстановить Anderson вместо Newton.

Различай статусы: запланирован, выполняется, обучение закончено, оценка закончена, ошибка, отложен. В отчёте сохраняй все seeds, включая неудачные и незавершённые.

## 6. Проверка сходимости после основной очереди

Сначала проведи парный аудит на капсулах исходных A-запусков. Для каждого seed выбери ближайшие доступные **training/actor_grad** capsules к 25k, 100k и 200k. Проверь полный batch=1024 и наличие actor, critics и loss_config. Запиши реальные шаги и правило выбора. Не выбирай только хорошие или только несошедшиеся батчи.

Одну и ту же capsule передавай в `audit` как `--checkpoint` и `--inputs`. Используй `--anderson-caps 25 100 500 --anderson-tol 1e-5 --warmup 2 --repeats 10`. Полная команда есть в `RUNNER_COMMANDS.md`. Получишь сравнение одинаковых параметров/наблюдений/шума, Newton и независимую FP64-проверку. Аудит выполняй после обучения на освободившихся ресурсах. При отсутствии подходящей капсулы сообщи об этом, не подменяй её несвязанным checkpoint.

Отчёт сохрани в каталоге кампании: таблица всех запусков и отдельная таблица аудита. Покажи U4/success/return по seed, длительность обучения и оценки, итерации/кривые residual, долю вызовов без сходимости при достижении cap, хвосты ошибок по примерам. Разделяй training/evaluation и используй их собственные знаменатели. В аудите покажи изменения действий, logp и SAC gradients, а также случаи невалидной FP64-reference.

**Интерпретация:** Anderson останавливается по среднему residual батча. Cap=500 — защитный предел с ранней остановкой, а не обещание полной сходимости каждого примера. Достижение cap и недостижение точности — разные события. Сравнение A/H меняет только бюджет итераций, A/T меняет и бюджет, и точность. Это не доказательство точной likelihood конечного sampler и не equal-wall-clock сравнение с SAC/DIME.
